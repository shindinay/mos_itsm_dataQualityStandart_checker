Информация о документе

Минимальная периодичность пересмотра:
Не реже одного раза в год
Ограничение доступа:
Нет

Стандарт устанавливает требования к данным, содержащимся в объектах MOS.ITSM. Данные, к которым предъявляются требования настоящего стандарта, содержатся в полях, которые являются контролируемыми и обязательными. 
Назначение документа

Стандарт предназначен для обеспечения наличия качественных данных в управляемых объектах MOS.ITSM, которые необходимы для комплексного и целостного процесса управления услугами и конфигурационными единицами. 
Цели документа

Документ подготовлен в целях обеспечения соблюдения критериев качества данных, необходимых для: 
Комплексного управления услугами и конфигурационными единицами в MOS.ITSM 
Определения ответственных лиц и их зон ответственности 
Планирования изменений по услугам 
Возможности использования данных в бизнес - процессах (например, на этапах утверждения и т.д.)
Формирования отчетности 
Ответственность и Область применения

Структурные подразделения, входящие в кластер «ИТ Решения» ДИТ г. Москвы, использующие платформу MOS.ITSM.
Нормативные роли 
Владелец стандарта – сотрудник структурного подразделения, назначенный на исполнение роли, указанием куратора кластера «ИТ Решения»:
назначает исполнителя роли «Менеджер практики»;
определяет цель создания стандарта;
определяет состав метрик для контроля соблюдения стандарта;
обеспечивает контроль и эскалацию по систематическим отклонениям норм стандарта.
Менеджер по практике – сотрудник, назначенный Владельцем стандарта на исполнение роли:
создает стандарт и согласовывает его с Владельцем стандарта;
контролирует исполнение стандарта;
обеспечивает наличие отчетности перечню метрик стандарта;
контролирует целостность и доступность стандарта;
инициирует и обрабатывает предложения и жалобы по стандарту и на основе выводов готовит рекомендации к Владельцу по оптимизации стандарта;
инициирует доработки в системах для исполнения стандарта.

Структура взаимодействия объектов 
Соглашения об уровне обслуживания формируются для каждой комбинации: «Предложение услуги» – «Компонент услуги» – «Клиент» (рисунок 1). Объекты «Предложение» и «Компонент услуги» являются дочерними к «Услуге». Один клиент может иметь несколько соглашений с разными предложениями по одной услуге. 
Если для одного и того же компонента услуги активно несколько соглашений, но с разными предложениями, то при расчете целевых показателей времени решения и реакции в запросе, автоматически будут использоваться значения из того предложения, в котором соответствующие значения меньше.

Статус
Значения доступные к выбору:

Расширение UI 
Используется для выбора расширения пользовательского интерфейса (UI) к шаблону запроса. 
Опционально
UI форма запроса должна обеспечивать возможность пользователю быстро и легко подать запрос:
1. UI форма запроса должна содержать текстовые подсказки, примеры заполнения полей и маски ввода
2 UI форма запроса (для исключения ошибок ввода данных) должна содержать корректные типы данных в соответствующих полях (пользовательские коллекции, данные из глобальных справочников и т.д.) и, по возможности, ручной ввод текста должен быть исключен
3. UI форма запроса должна быть структурирована и достаточна (пользователь должен понимать, что и в какой последовательности ему необходимо заполнить в UI, а специалисты должны получать достаточный объем сведений от пользователя для оказания услуги).
4. UI формы запросов должны быть лаконичными (использование контекстно зависимых элементов UI) и спроектированы в едином стиле, в т.ч. для дальнейшей возможности их тиражирования.
