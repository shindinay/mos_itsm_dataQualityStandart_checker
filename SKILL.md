# mos_itsm_dataQualityStandart_checker

Скилл проверяет объект «Услуга» (service) МосИТСМ и все связанные с ним объекты на соответствие
«Стандарту качества данных в объектах MOS.ITSM» и формирует отчет в формате Markdown.

Вход: ссылка на карточку Услуги (или её ID), при необходимости — среда (QA/ПРОД).
Выход: файл `report_<id>.md` с перечнем проверенных объектов (со ссылками) и выявленными
несоответствиями с предложениями по исправлению.

## Конфигурация

Параметры окружения — в `skill_env.json` рядом с этим файлом:
`MOSITSM_API_URL_PROD` / `MOSITSM_API_URL_QA` — базовые URL API,
`MOSITSM_ACCOUNT` (значение `community`), токены `MOSITSM_PERS_TOKEN_QA` / `MOSITSM_PERS_TOKEN_PROD`,
`MOSITSM_STAGE` — среда по умолчанию (сейчас QA), `LOCAL_STANDART_LINK` — путь к docx-оригиналу стандарта.
Среда определяется из URL карточки (itsm-qa → QA, itsm → ПРОД) или из запроса пользователя.

## Шаг 1 — Выгрузи услугу и все связанные объекты

```bash
cd "<папка скилла>"
python scripts/fetch_service_tree.py --service https://community.itsm-qa.mos.ru/services/12345
# или: python scripts/fetch_service_tree.py --service 12345 --env PROD --out tree.json
```

Скрипт скачает услугу, её компоненты (service_instances), предложения (service_offerings),
SLA (для каждого компонента) и шаблоны запросов, и сложит всё в один JSON
(по умолчанию `service_tree_<id>.json`). Он печатает краткую сводку и ссылку на карточку.
Если токена для ПРОД нет в `skill_env.json` — запроси его у пользователя, не угадывай.

## Шаг 2 — Прочитай критерии проверки

Прочитай `references/standart_checks.md` — это выжимка стандарта с привязкой к полям API:
какие поля обязательные/контролируемые для Услуги, Компонента услуги, Предложения, SLA
и Шаблона запроса, и какое требование к каждому полю. Оригинал стандарта —
`LOCAL_STANDART_LINK` (docx), обращайся к нему, только если случая нет в выжимке.

## Шаг 3 — Проверь каждый объект

Для каждого объекта из JSON пройди по списку обязательных и контролируемых полей
из `references/standart_checks.md`:

1. **Полнота**: обязательное поле пусто (null/пустая строка/пустой массив) → несоответствие.
2. **Актуальность**: ссылочное поле указывает на неактивную запись (если статус виден) → несоответствие.
3. **Точность**: имя объекта не соответствует ни одному допустимому синтаксису → несоответствие.
   Синтаксис проверяй по смыслу (наличие характерных частей: разделитель «.» с уровнем/средой
   для компонентов и предложений, «Соглашение – Поставщик – Клиент – …» для SLA и т.п.),
   не строгими regex. Если уверенности нет — формулируй как подозрение, а не как нарушение.
4. Для ключевых слов: у услуги ≥ 2, у шаблона запроса ≥ 3.
5. Для лиц (владелец, менеджеры, представители, SLA-менеджер): активная запись,
   sAMAccountName не пуст (роль сотрудника из API не видна — проверяй только заполненность,
   а проверку роли упоминай как требование стандарта, которое нужно проверить вручную).

Не выдумывай несоответствий: если поле контролируемое, но стандарт допускает «Не установлено» —
это не нарушение. Поля «Автомат.» не проверяй вообще.

## Шаг 4 — Сформируй отчет

Сохрани `report_<id>.md` в папке скилла по шаблону из раздела «Шаблон отчета» в
`references/standart_checks.md`. Обязательно:

- перечень всех проверенных объектов с ссылками на карточки:
  `{web_base}/services/<id>`, `{web_base}/service_instances/<id>`,
  `{web_base}/service_offerings/<id>`, `{web_base}/slas/<id>`, `{web_base}/request_templates/<id>`
  (web_base печатает скрипт в поле `meta.web_base`);
- по каждому объекту: что соответствует (кратко), и по каждому несоответствию —
  **критерий** (Полнота/Актуальность/Точность), **что не так** и
  **предложение по исправлению** (конкретное: какое поле, каким содержимым заполнить);
- сводная таблица и выводы с приоритизацией: сначала несоответствия обязательных полей активных
  (продакшн) объектов, затем контролируемых.

Если объекты не найдены (например, у услуги нет SLA) — это нормально, укажи «нет объектов»
в сводке; отсутствие самих компонентов/предложений у услуги не является нарушением стандарта,
но если у услуги не заполнены её собственные обязательные поля — это нарушение.

## Шаг 5 — Верни результат

Покажи пользователю путь к отчету, ссылку на услугу и краткое резюме:
сколько объектов проверено, сколько несоответствий найдено, 2–3 самых критичных.
Сам отчет приводить целиком в чате не нужно.

## Файлы скилла

- `scripts/fetch_service_tree.py` — выгрузка услуги и связанных объектов в один JSON.
- `references/standart_checks.md` — критерии проверки по стандарту с привязкой к полям API + шаблон отчета.
- `LOCAL_STANDART_LINK` из `skill_env.json` — оригинал стандарта (docx).
