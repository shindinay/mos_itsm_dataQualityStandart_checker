# Стандарт качества данных в объектах MOS.ITSM — выжимка для проверки

Источник: «Стандарт качества данных в объектах MOS.ITSM» (ред. 1, 13.11.2023; владелец Пакина Т.С., менеджер по практике Лаврова Н.С.).
Проверять нужно только **контролируемые** и **обязательные** поля («Обяз.» = обязательное, «Автомат.» = заполняется системой — не проверять вручную). Непроверяемые вручную поля (Изображение, Опрос, Компоненты родительской/дочерней услуги, Соглашения об уровне обслуживания — списки отображения) в отчет включать не нужно, кроме случаев когда они указаны ниже.

Общие правила, применимые ко всем ссылочным полям:
- ссылка на справочник «Лица»: запись активна, атрибут sAMAccountName не пуст;
- ссылка на справочник «Организации»: запись в статусе «Активно»;
- ссылка на справочник «Команды»: запись в статусе «Активно»;
- поля со «списком доступных значений»: значение из разрешенного списка.

Несоответствие = поле пустое, хотя оно обязательное/контролируемое, либо значение не удовлетворяет требованию стандарта.

## 1. Услуга (service)

| Поле | Тип | Требование |
|---|---|---|
| Имя (`name`) | Обяз. | Синтаксис один из: «КЕ, подлежащая управлению в рамках оказания услуги»; «Конечный результат оказания услуги»; «Наименование, закрепленное в нормативном документе или ГК». Имя уникально среди услуг разных Поставщиков |
| Отключено (`disabled`) | Контрол. | Флажок установлен только когда услуга выведена из эксплуатации |
| Ключевые слова (`keywords`) | Обяз. | Не менее двух ключевых слов; не включать их в имя/описание услуги |
| Описание (`description`) | Обяз. | Позволяет клиенту однозначно понять конечный результат оказания услуги |
| Поставщик услуги (`provider`) | Обяз. | Организация в статусе «Активно» |
| Команда первой линии (`first_line_team`) | Обяз. | Команда в статусе «Активно» |
| Команда поддержки (`support_team`) | Контрол. | Команда в статусе «Активно» |
| Владелец услуги (`service_owner`) | Обяз. | Лицо: статус «Активно», sAMAccountName не пуст |
| Менеджер релиза (`release_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст, роль «Менеджер релизов» |
| Менеджер изменения (`change_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст, роль «Менеджер рабочего процесса» |
| Менеджер базы знаний (`knowledge_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст, роль «Менеджер знаний» |
| Менеджер проблемы (`problem_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст, роль «Менеджер проблем» |
| Менеджер доступности (`availability_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст |
| Менеджер мощностей (`capacity_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст |
| Менеджер по непрерывности (`continuity_manager`) | Контрол. | Лицо: актив, sAMAccountName не пуст |

Примечание: поле «Категория» (`service_category`) — необязательное, в отчет можно включать как рекомендацию, если пусто.

## 2. Компонент услуги (service_instance)

| Поле | Тип | Требование |
|---|---|---|
| Имя (`name`) | Обяз. | Синтаксис один из: «Наименование услуги», «элемент услуги или конфигурации»; «Конфигурационная единица», «среда»; «Наименование услуги», «среда». Примеры: «Учетная запись и права доступа. HPSM», «Электронная почта. Prod» |
| Статус (`status`) | Обяз. | Готовится / В производстве (`in_production`) / Прекращено |
| Услуга (`service`) | Обяз. | Услуга в статусе «Активно» |
| Команда первой линии | Контрол. | Команда в статусе «Активно» (в API в объекте не отдельное поле — см. `support_team`) |
| Команда поддержки (`support_team`) | Контрол. | Команда в статусе «Активно» |
| Конфигурационные единицы | Опционально | Компонент всегда должен быть связан с управляемым объектом (КЕ) |

## 3. Предложение услуги (service_offering)

| Поле | Тип | Требование |
|---|---|---|
| Имя (`name`) | Обяз. | Синтаксис один из: «Наименование услуги», «Уровень предложения»; «Компонент услуги», «Уровень предложения»; «Компонент услуги», «Наименование предложения». Пример: «Учетная запись и права доступа. Стандарт» |
| Статус (`status`) | Обяз. | Запланировано / Не опубликовано / Доступно (`available`) / Временно недоступно / Прекращено |
| Услуга (`service`) | Обяз. | Услуга в статусе «Активно» |
| Часы обслуживания (`support_hours` в SLA; для предложения — календарь) | Обяз. | Запись из списка доступных значений |
| Доступность % (`availability`) | Обяз. | Числовой тип данных |
| Надежность (`reliability`) | Обяз. | Числовой тип данных |
| Производительность (`performance`) | Контрол. | Текстовый тип данных |
| Целевые показатели времени реакции и решения (`response_target_*`, `resolution_target_*`) | Опционально | Числовой тип данных; заполняются по необходимости для категорий запросов |

## 4. Соглашение об уровне обслуживания (sla)

| Поле | Тип | Требование |
|---|---|---|
| Имя (`name`) | Обяз. | Синтаксис один из: «Соглашение – Наименование поставщика – Наименование Клиента – Компонент услуги»; «Соглашение – Наименование поставщика – Наименование Клиента – Услуга»; «Наименование поставщика – Наименование Клиента – Услуга». Пример: «Соглашение – ДИТ. Сервис – менеджер – ГКУ Инфогород - Учетная запись и права доступа» |
| Статус (`status`) | Обяз. | Готовится (`being_prepared`) / Запланирована активация / Активный (`active`) / Просрочено (`expired`) |
| Клиент (`customer`) | Обяз. | Организация в статусе «Активно» |
| Представители клиента (`customer_rep`) | Обяз. | Лицо: актив, sAMAccountName не пуст |
| Менеджер уровня обслуживания (`service_level_manager`) | Обяз. | Лицо: актив, sAMAccountName не пуст, роль «Менеджер уровня услуги» |
| Предложение услуг (`service_offering`) | Обяз. | Предложение в статусе «Активно» (Доступно) |
| Компонент услуги (`service_instance`) | Обяз. | Компонент в статусе «Активно» (В производстве) |
| Дата начала (`start_date`) | Обяз. | Заполнена |
| Покрытие (`coverage`) | Обяз. | Запись из списка доступных значений |

Примечание: «Домен клиента» (`customer_account`) — опционально; «Поставщик услуг» — автомат., не проверять.

## 5. Шаблон запроса (request_template)

| Поле | Тип | Требование |
|---|---|---|
| Тема (`subject`) | Обяз. | Синтаксис один из: «Дифференцированный конечный результат оказания услуги»; «Действие с объектом управления услуги или ее компонента». Примеры: «Консультирование по работе в системе», «Изменение прав доступа» |
| Услуга (`service`) | Обяз. | Услуга в статусе «Активно» |
| Ключевые слова (`keywords`) | Контрол. | Не менее трех ключевых слов |
| Категория (`category`) | Обяз. | Запись из списка доступных значений |
| Команда (`team`) | Обяз. | Команда в статусе «Активно» |
| Статус (`status`) | Обяз. | Запись из списка доступных значений |
| Влияние (`impact`) | Контрол. | Для категории «Инцидент» (не обязателен для остальных) |
| Видимость (конечные пользователи / специалисты) (`end_users`, `specialists`) | Контрол. | Если оба чек-бокса сняты — шаблон доступен только через REST API (отметить как замечание) |
| Расширение UI (`ui_extension`) | Опционально | Если задано: форма должна содержать подсказки/маски, корректные типы данных, быть структурированной и лаконичной (в отчет — рекомендация, автоматически не проверяется) |

## Что считать несоответствием

1. Обязательное поле пусто (null) — несоответствие «Полнота».
2. Ссылочное поле указывает на неактивную запись — несоответствие «Актуальность» (если статус записи виден в API).
3. Имя не соответствует ни одному допустимому синтаксису — несоответствие «Точность». Проверку синтаксиса выполняй по смыслу (по наличию характерных частей: разделитель «.» между наименованием и уровнем/средой для компонентов и предложений; префикс «Соглашение – …» или «Поставщик – Клиент – …» для SLA), а не строгим regex, и формулируй замечание как подозрение, если уверен не на 100%.
4. Числовое обязательное поле (доступность, надежность) пусто — несоответствие.
